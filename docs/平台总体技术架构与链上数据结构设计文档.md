 ## 二、链上数据结构设计
 
 ### 2.1 ERC-3525 数据模型
 
 本平台使用 **ERC-3525 (Semi-Fungible Token, SFT)** 作为 RWA 资产凭证的基础协议。ERC-3525 兼具 ERC-721 的**唯一标识性**与 ERC-20 的**可拆分性**，完美适配应收账款凭证的建模需求。
 
 #### 核心数据结构
 
 ```
 Token ───────────────────────────────────┐
 ├── tokenId: uint256        ← 全局唯一编号 │
 ├── slot: uint256           ← 品类槽位     │ (同一到期日 & 合同锚定的凭证属于同一 slot)
 ├── value: uint256          ← 当前金额     │ (支持拆分转移部分金额)
 ├── owner: address          ← 当前持有人   │
 └── approvals:              ← 授权映射     │
     └── operator => allowance              │
                                            │
 RWA Extension ────────────────────────────┤
 ├── issuer: address         ← 签发企业     │ (核心企业)
 ├── faceValue: uint256      ← 原面值       │ (签发时原始金额)
 ├── maturityDate: uint256   ← 到期日       │
 ├── status: AssetStatus     ← 资产状态     │
 │   ├── Active = 0                         │
 │   ├── Frozen = 1                         │
 │   ├── Revoked = 2                        │
 │   └── Settled = 3                        │
 ├── underlyingContractHash: string ← 合同哈希
 └── metadataURI: string     ← 元数据 URI
 ```
 
 ### 2.2 Slot（品类槽位）设计
 
 Slot 是 ERC-3525 中的核心概念，用于划分凭证的品类。在本平台中，Slot 编码规则如下：
 
 ```
 Slot 编码 = keccak256(issuer ++ maturityDate ++ contractCategory) % 2^256
 
 其中:
   issuer           = 签发核心企业地址
   maturityDate     = 到期日时间戳（Unix秒）
   contractCategory = 合同品类枚举（采购合同=1, 服务合同=2, 租赁合同=3...）
 ```
 
 **设计原则**：同一核心企业在同一到期日签发的同品类凭证属于同一 Slot，确保价值可互换；不同到期日或不同品类的凭证不可混用。
 
 ### 2.3 资产生命周期状态机
 
 ```
                        ┌─────────────────────────────────────────┐
                        │           签发 (Mint)                    │
                        │  核心企业签署链上确权凭证                │
                        └──────────────┬──────────────────────────┘
                                       │
                                       ▼
                          ┌──────────────────────┐
              ┌───────────│    Active (活跃)       │────────────┐
              │           └──────────────────────┘            │
              │                     │                         │
              ▼                     ▼                         ▼
   ┌──────────────────┐  ┌──────────────────┐  ┌──────────────────┐
   │  Frozen (冻结)    │  │ 流转/拆分/融资    │  │ Revoked (废止)   │
   │  监管/争议触发    │  │ 多次流转          │  │ 核心企业撤销     │
   └──────────────────┘  └──────────────────┘  └──────────────────┘
              │                     │
              │                     ▼
              │           ┌──────────────────┐
              └───────────│  Settled (已兑付) │
                          │  到期自动清算完成  │
                          └──────────────────┘
 ```
 
 ### 2.4 关键事件日志设计
 
 | 事件名称                  | 参数                                              | 触发时机                           |
 |---------------------------|---------------------------------------------------|------------------------------------|
 | `AssetCreated`            | tokenId, issuer, slot, faceValue, maturityDate    | 核心企业签发新凭证                  |
 | `AssetValueTransferred`   | fromTokenId, toTokenId, value                     | 凭证拆分/合并时                    |
 | `AssetOwnershipTransferred` | fromTokenId, from, to, value                    | 凭证完整转账时                      |
 | `AssetSplit`              | parentTokenId, childTokenId1, childTokenId2       | 凭证一拆二时                        |
 | `AssetMerged`             | tokenId1, tokenId2, newTokenId                    | 两个同 slot 凭证合并时              |
 | `AssetStatusChanged`      | tokenId, oldStatus, newStatus                     | 冻结/废止/兑付状态变更              |
 | `AssetRevoked`            | tokenId, reason                                   | 核心企业废止凭证                    |
 | `AssetSettled`            | tokenId, amount                                   | 到期自动清算完成                    |

 ## 三、合约交互规范
 
 ### 3.1 合约角色定义
 
 | 合约角色       | 角色标识 (bytes32)         | 说明                                         |
 |----------------|----------------------------|----------------------------------------------|
 | 平台管理员     | `DEFAULT_ADMIN_ROLE`       | 全局管理员，可授予/撤销角色                   |
 | 核心企业       | `CORE_ENTERPRISE_ROLE`     | 可签发 RWA 凭证的核心企业账户                 |
 | 供应商         | `SUPPLIER_ROLE`            | 可接收和流转凭证的供应商账户                   |
 | 金融机构       | `FINANCIAL_INSTITUTION_ROLE` | 可核验凭证并提供融资贴现的银行账户           |
 | 审计员         | `AUDITOR_ROLE`             | 可查看全量链上数据但不可写入                   |
 
 ### 3.2 核心接口规范
 
 #### RWA 扩展接口
 
 ```solidity
 /// @notice 签发新的 RWA 资产凭证（仅 CORE_ENTERPRISE_ROLE）
 /// @param to 接收方（通常为一级供应商）
 /// @param slot 品类槽位
 /// @param value 凭证面值（单位：分/wei）
 /// @param maturityDate 到期日时间戳
 /// @param contractHash 底层采购合同哈希
 /// @param uri 元数据 URI
 /// @return tokenId 新签发凭证 ID
 function mintRWAAsset(
     address to,
     uint256 slot,
     uint256 value,
     uint256 maturityDate,
     string calldata contractHash,
     string calldata uri
 ) external returns (uint256 tokenId);
 
 /// @notice 废止资产（仅签发核心企业可调用）
 /// @param tokenId 要废止的凭证 ID
 /// @param reason 废止原因
 function revokeAsset(uint256 tokenId, string calldata reason) external;
 
 /// @notice 冻结/解冻资产（仅金融机构或管理员）
 /// @param tokenId 凭证 ID
 /// @param frozen true=冻结, false=解冻
 function setAssetFrozen(uint256 tokenId, bool frozen) external;
 
 /// @notice 获取资产完整信息
 /// @param tokenId 凭证 ID
 /// @return RWAAsset 结构化资产数据
 function getAssetInfo(uint256 tokenId)
     external
     view
     returns (
         uint256 slot,
         address issuer,
         uint256 faceValue,
         uint256 maturityDate,
         uint8 status,
         string memory contractHash,
         string memory uri
     );
 
 /// @notice 查询指定签发人签发的所有活跃凭证 ID
 /// @param issuer 签发人地址
 /// @return tokenIds 凭证 ID 列表
 function getIssuedAssets(address issuer)
     external
     view
     returns (uint256[] memory tokenIds);
 ```
 
 #### 标准 ERC-3525 继承接口
 
 | 函数签名                                                                 | 功能                 |
 |--------------------------------------------------------------------------|----------------------|
 | `balanceOf(uint256 tokenId) → uint256`                                   | 查询某凭证金额       |
 | `ownerOf(uint256 tokenId) → address`                                     | 查询凭证持有人       |
 | `slotOf(uint256 tokenId) → uint256`                                      | 查询品类槽位         |
 | `approve(uint256 tokenId, address operator, uint256 value)`              | 授权操作者处理部分金额 |
 | `allowance(uint256 tokenId, address operator) → uint256`                 | 查询授权额度          |
 | `transferFrom(uint256 fromTokenId, address to, uint256 value)`           | 转账部分/全部金额到新凭证 |
 | `transferFrom(uint256 fromTokenId, uint256 toTokenId, uint256 value)`    | 合并金额到已有凭证   |
 | `totalSupply() → uint256`                                                | 查询总凭证数          |
 | `name() → string` / `symbol() → string`                                  | 元数据               |
 
 ### 3.3 调用时序规范
 
 #### 资产签发流程
 
 ```
 [核心企业]         [后端 API]            [合约 RWA_Core_Asset]      [链底座]
      │                 │                        │                     │
      │  1. 上传合同    │                        │                     │
      │────────────────>│                        │                     │
      │                 │  2. 计算合同哈希        │                     │
      │                 │  3. 计算 slot           │                     │
      │                 │  4. 签名交易并提交      │                     │
      │                 │───────────────────────>│                     │
      │                 │                        │  5. 验证角色权限    │
      │                 │                        │  6. 创建 Token      │
      │                 │                        │  7. 记录资产元数据  │
      │                 │                        │  8. 写入区块        │
      │                 │                        │────────────────────>│
      │                 │                        │  9. 交易收据返回    │
      │                 │<───────────────────────│                     │
      │  10. 签发成功   │                        │                     │
      │<────────────────│                        │                     │
 ```
 
 #### 资产流转(拆分)流程
 
 ```
 [持有人A]          [持有人B]          [合约 RWA_Core_Asset]      [链底座]
      │                 │                     │                     │
      │  1. 发起拆分    │                     │                     │
      │  transferFrom(  │                     │                     │
      │   tokenId, B,   │                     │                     │
      │   value=300)    │                     │                     │
      │──────────────────────────────────────>│                     │
      │                 │                     │  2. 验证 allowance  │
      │                 │                     │  3. 扣减源凭证金额  │
      │                 │                     │  4. 创建新凭证      │
      │                 │                     │     (自动生成ID)    │
      │                 │                     │  5. 新凭证归 B 所有 │
      │                 │                     │  6. 触发 Split 事件 │
      │                 │                     │────────────────────>│
      │                 │                     │  7. 写入区块        │
      │                 │<────────────────────│                     │
      │                 │  8. 收到拆分后凭证  │                     │
 ```

 ## 四、链上数据存储与索引设计
 
 ### 4.1 MySQL 链下缓存表结构
 
 | 表名                | 用途                         | 核心字段                                                              |
 |---------------------|------------------------------|-----------------------------------------------------------------------|
 | `rwa_asset`         | RWA 凭证缓存表               | token_id, slot, issuer, owner, value, face_value, maturity_date, status, contract_hash, metadata_uri, created_block, tx_hash |
 | `rwa_transfer_log`  | 流转/拆分事件日志            | event_type, from_token, to_token, from_addr, to_addr, value, block_number, tx_hash, timestamp |
 | `rwa_enterprise`    | 企业注册信息                 | enterprise_address, name, role(核心企业/供应商/银行), credit_rating, certificate |
 | `rwa_asset_snapshot`| 资产每日快照                 | token_id, snapshot_date, holder, value                               |
 
 ### 4.2 链上 Merkle 化存储策略
 
 为实现高效验证与数据压缩，同一核心企业的批量签发操作将组织为 Merkle 树：
 
 - 根哈希上链存储，降低 Gas 消耗
 - 各子凭证的 inclusion proof 在链下生成，供验证者查询

 ## 五、安全与权限控制规范
 
 ### 5.1 角色权限矩阵
 
 | 操作 \\ 角色          | 管理员 | 核心企业 | 供应商 | 金融机构 | 审计员 |
 |----------------------|--------|----------|--------|----------|--------|
 | 签发 RWA 凭证        | ✓      | ✓        | ✗      | ✗        | ✗      |
 | 废止自有凭证         | ✗      | ✓        | ✗      | ✗        | ✗      |
 | 冻结凭证             | ✓      | ✗        | ✗      | ✓        | ✗      |
 | 接收/流转凭证        | ✗      | ✓        | ✓      | ✓        | ✗      |
 | 查看全量链上数据     | ✓      | ✓专属    | ✗      | ✓专属    | ✓      |
 | 查看凭证金额明细     | ✓      | 签发方   | 持有方  | 核验方   | ✓      |
 | 授予/撤销角色        | ✓      | ✗        | ✗      | ✗        | ✗      |
 
 ### 5.2 防重入与整数安全
 
 - 所有外部调用（`call`/`transfer`）均遵循 Checks-Effects-Interactions 模式
 - 使用 OpenZeppelin `ReentrancyGuard` 修饰器
 - Solidity 0.8+ 内置溢出检查
